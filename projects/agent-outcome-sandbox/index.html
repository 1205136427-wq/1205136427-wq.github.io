PROLOGUEWHY THIS EXISTS

回答可以被生成。
业务结果不能。

传统评测问模型：“你说得对吗？”
业务评测追问系统：“事情真的办成了吗？”

这个项目把真实流程做成数字孪生，让 Agent 在权限、规则和状态机里行动，再用轨迹、页面与门禁共同证明结果。

01

REAL WORLD真实现场

故事从一张报销单开始。

周五下午，小张提交一张 3000 元差旅报销。经理判断业务是否真实、预算是否合理；财务复核发票与金额。流程不是一个角色做完，而是一棒接一棒。

接力

每一棒都由另一个真实角色接住。不是同一个 Agent 在后台切换身份，而是三份权限、三次判断、三条留痕。

3 actors · 3 decisions · 1 case

06

LEGAL REJECTION合法驳回

驳回，不是事故。
绕过驳回，才是。

发票抬头不符、金额异常、预算不成立，都可能让流程回到员工手里。合规驳回是业务流程的一部分；关键是它必须由有权限的角色发起、说明原因、留下轨迹。

业务不真实，驳回是正确动作。

经理发现单据写的是私人行程，在 submitted 状态发起 reject。系统要求填写原因，随后单据进入 rejected。

REJECT REASON

01谁能驳回？

经理只能在 submitted 驳回到 rejected；财务只能在 manager_approved 驳回。角色和起点都受状态机约束。

02谁能修改？

只有报销人自己能把 rejected 单据 revise 回 draft。revision_count 增加，驳回原因被清除。

03怎样算办对？

当任务目标就是“正确驳回”时，终态与原因同样是可判分的业务结果，而不是 happy path 的例外。

↺
正常的驳回会形成闭环。

员工补充发票、修正金额、重新提交。流程继续，证据链也不断。

错误不是“有驳回”
错误是越权驳回、无原因驳回或绕过审批。

PROJECT NOTES项目说明

一个把业务结果
变成可验证事实的沙箱。

Agent 业务结果评测沙箱不评价一段回答像不像，而是验证 Agent 是否在权限、规则和状态机内，把一件事真正办完。

WHAT THIS PROJECT IS

Agent 业务结果评测沙箱

它把真实业务流程做成可执行、可回放、可判分的数字孪生：场景包定义数据、角色、状态与规则；Agent 只能通过 BusinessAPI 提交业务动作；确定性内核依次执行权限、Guard、状态迁移与 Effect。

同一套机制已经覆盖报销、采购、合同与短视频生成。业务状态、审批链、产物规格和发布结果由状态机与轨迹判定；主观创意与审美质量交给人工量表或额外评估器，不伪装成确定性结论。

TECHNICAL LAYERS

技术点，不是装饰。

从场景声明到上线门禁，每一层都解释结论从哪里来、如何被质疑、如何被复现。

01SCENARIO DSL

业务即配置

用 flow.yaml、seed.json、expected.yaml 声明状态、权限、硬规则、Effect、目标谓词和初始数据。

02BUSINESS API

身份不可自报

演员身份绑定在会话上下文。Agent 不能声称自己是经理，也没有绕开业务动作直接写数据库的入口。

03DETERMINISTIC KERNEL

失败即关闭

权限、Guard、状态迁移、Effect 和软规则依次执行；任一硬规则失败，都不产生业务写入。

04TRACE / REPLAY

结果可复算

完整记录动作、入参、前后状态、Effect、违规与耗时；再用快照回放，从同一初始世界复现结果。

05RED TEAM / GUI

过程与页面同验

红队验证越权、注入、幻觉和错误工具调用；Playwright 视觉回归与联合判分防止页面正确掩盖后台错误。

06RUNTIME

模型可替换

支持 DeepSeek、OpenAI 兼容接口与 LangGraph 适配器；可选 C++ 加速内核。判定不依赖 LLM 主观裁决。

能力边界

状态机适合验证“是否按权限和流程办成”，不适合单独判断“视频是否好看”或“文案是否有创意”。画面、字幕、音频版权、审美与叙事质量需要人工量表、多模态模型或专用 artifact validator；异步生成任务还需要 job adapter，把渲染开始、完成和失败转成可追踪业务事件。
